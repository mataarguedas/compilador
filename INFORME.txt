2. DESCRIPCIÓN DEL ANALIZADOR LÉXICO Y ALCANCE
---------------------------------------------------------------------------------------------------
El programa implementa la etapa de análisis léxico de un compilador para el lenguaje PHP. Es una
aplicación de consola escrita en Java puro, sin librerías externas y sin expresiones regulares.
Realiza cuatro tareas:

  a) Busca el archivo .php que está en la misma carpeta que el .jar y lo lee sin alterar su
     formato (espacios, tabulaciones, líneas en blanco y saltos de línea originales).
  b) Divide el texto en tokens (lexemas) mediante autómatas escritos a mano, carácter por
     carácter.
  c) Valida las etiquetas de apertura y cierre (<?php y ?>), los identificadores que aparecen a
     la izquierda del operador de asignación = y los comentarios de línea (// y #).
  d) Genera el archivo <nombre>-errors.log con una copia numerada del código fuente y, al final,
     la lista de errores encontrados (uno por línea, con su código, su número de línea y una
     descripción específica).

Alcance: solo el análisis léxico. No se realiza análisis sintáctico ni semántico (por ejemplo,
no se detectan variables sin declarar). Las limitaciones se detallan en la sección 11.


3. REQUISITOS
---------------------------------------------------------------------------------------------------
  - Java (JDK o JRE) versión 8 o superior. El código solo usa características de Java 8.
  - El comando "java" debe estar disponible en el PATH.

Cómo comprobarlo: abra una ventana de CMD y escriba

      java -version

Debe aparecer un texto similar a:

      openjdk version "25.0.4" 2026-07-21 LTS

(cualquier versión 1.8 o superior sirve). Si aparece "java no se reconoce como un comando
interno o externo", consulte la sección 10.

Para compilar desde el código fuente se necesita además el JDK (javac) y NetBeans o Apache Ant
(NetBeans ya incluye Ant).

4.3 Las cuatro etapas del análisis léxico

  ETAPA 1 - OBTENCIÓN DE TOKENS (paquete lexer)
    CharacterStream  Recorre el texto carácter por carácter; lleva posición, línea y columna
                     (\r\n cuenta como un solo salto de línea); permite mirar adelante (peek),
                     consumir (advance) y retroceder (mark/reset).
    LexerMode        Dos modos: INLINE (fuera de PHP) y PHP (dentro de <?php ... ?>).
    Lexer            Bucle principal. En modo PHP prueba los patrones en este orden: salto de
                     línea, espacios, cierre ?>, comentario de línea, comentario de bloque,
                     cadena, variable, número, palabra y operador. Si ningún patrón acepta el
                     carácter, produce un token UNKNOWN. En modo INLINE solo reconoce <?; el
                     resto es texto INLINE_TEXT. Nunca se pierde un carácter: la concatenación
                     de todos los lexemas es idéntica al archivo (LexemeInvariant lo verifica).

  ETAPA 2 - CLASIFICACIÓN DE TOKENS (paquete lexer)
    TokenType        Tipos: OPEN_TAG, CLOSE_TAG, INLINE_TEXT, VARIABLE, IDENTIFIER, KEYWORD,
                     INTEGER_LITERAL, FLOAT_LITERAL, STRING_LITERAL, INLINE_COMMENT,
                     BLOCK_COMMENT, ASSIGN, COMPARISON_OPERATOR, ARITHMETIC_OPERATOR,
                     LOGICAL_OPERATOR, CONCAT_OPERATOR, OTHER_OPERATOR, SEMICOLON, COMMA,
                     LPAREN, RPAREN, LBRACE, RBRACE, LBRACKET, RBRACKET, WHITESPACE, NEWLINE,
                     UNKNOWN, MALFORMED_NUMBER, UNTERMINATED_STRING, UNTERMINATED_COMMENT.
    TokenCategory    Categoría de cada tipo: TAG, KEYWORD, IDENTIFIER, LITERAL, OPERATOR,
                     DELIMITER, COMMENT, LAYOUT, INLINE_TEXT o ERROR.
    Token            Tipo, lexema, línea, columna, línea final y la marca "reported".
    TokenClassifier  Asigna el tipo final: una palabra es KEYWORD si es palabra reservada; un
                     operador recibe su tipo (= es ASSIGN, == es COMPARISON_OPERATOR, ; es
                     SEMICOLON, etc.).
    ReservedWords    Las 20 palabras reservadas del enunciado.

  ETAPA 3 - DETERMINACIÓN DE PATRONES (LÓGICA EQUIVALENTE) (paquete lexer.pattern)
    Cada patrón implementa la interfaz LexemePattern (canStart y match) y es un autómata
    escrito a mano. No se usa java.util.regex. La expresión regular equivalente de cada uno es:

      NewlinePattern        \r\n|\r|\n
      WhitespacePattern     [ \t]+
      OpenTagPattern        <\?(=|[ \t]*[pP]([hH][pP]?)?)?
      CloseTagPattern       \?>
      InlineCommentPattern  (//|#)[^\r\n]*
      BlockCommentPattern   /\*([^*]|\*+[^*/])*\*+/
      StringPattern         q([^q\\]|\\.)*q     (q es ', " o `)
      VariablePattern       \$[A-Za-z0-9_]*
      NumberPattern         D | D\.D? | \.D | exponentes [eE][+-]?D | 0x.. | 0b.. | 0o..
                            (D = [0-9](_?[0-9])*); seguido de [A-Za-z0-9_] => MALFORMED_NUMBER
      WordPattern           [A-Za-z_][A-Za-z0-9_]*
      OperatorPattern       ===|==|=|... (coincidencia más larga sobre la tabla de operadores)

    Los patrones más complejos (VariablePattern, NumberPattern, StringPattern y
    BlockCommentPattern) usan un enum State con un ciclo de transiciones explícito. La tabla
    de transiciones está en el Javadoc de cada clase. PatternRegistry define el orden de prueba.

  ETAPA 4 - VALIDACIÓN DE LEXEMAS (paquete validation)
    Validator (interfaz) y ValidationContext (fuente + tokens). ValidationPipeline ejecuta los
    validadores en este orden fijo:
      1. OpeningTagValidator   Etiqueta de apertura <?php       (códigos 100-106)
      2. ClosingTagValidator   Etiqueta de cierre ?>            (códigos 110-116)
      3. IdentifierValidator   Identificadores a la izquierda de = (códigos 200-205), con
                               AssignmentTargetExtractor y AssignmentTarget
      4. CommentValidator      Comentarios                       (códigos 300-304)
      5. LexemeValidator       Cadenas, caracteres y números     (códigos 400-402)
    Un token que ya generó un error de identificador queda marcado como "reported" y los
    validadores posteriores no lo vuelven a reportar.

compilación, así que los cambios deben hacerse en los archivos de la carpeta raíz.

Pruebas automáticas (opcional, sin JUnit), desde la raíz del proyecto:

      javac -encoding UTF-8 -d build\fixtures -cp build\classes test\compilador\FixtureRunner.java

  Debe terminar con "16 passed, 0 failed, 16 total".


6. EJECUCIÓN PASO A PASO DESDE CMD
---------------------------------------------------------------------------------------------------
  1. Abrir CMD: tecla Windows, escribir "cmd" y presionar Enter.
  2. Ir a la carpeta dist del proyecto, por ejemplo:

        cd C:\dev\compilador\dist

  3. La compilación ya deja codigo.php en esa carpeta. Para analizar otro archivo, copiarlo en
     esa misma carpeta, junto a compilador.jar:

        copy C:\ruta\del\archivo\codigo.php .

  4. Ejecutar:

        java -jar compilador.jar

     El programa busca en la carpeta del .jar todos los archivos cuyo nombre termina
     exactamente en ".php" (en minúscula), los analiza en orden alfabético y genera un log por
     cada uno. No hace falta indicar el nombre del archivo ni ninguna configuración. Los
     archivos con otra extensión (.PHP, .php.txt, .phtml, .txt) se listan como ignorados.

  5. Ver el resultado:

        type codigo-errors.log

Argumento opcional: se puede indicar un archivo concreto:

        java -jar compilador.jar codigo.php

  Si el archivo no termina en ".php" se muestra:
     ERROR: 'codigo.txt' does not have the required .php extension; the file was not processed.

Opción --tokens (o -t): además muestra en consola la tabla de tokens (línea, columna, tipo,
categoría y lexema) y confirma que la concatenación de lexemas es igual al archivo:

        java -jar compilador.jar --tokens

Códigos de salida:
  0  Se analizó al menos un archivo (aunque tenga errores léxicos).
  1  No se encontró ningún .php, la extensión es incorrecta o hubo un error de lectura o
     escritura (por ejemplo, carpeta de solo lectura).

     En caso de que se quiera hacer directamente de netbeans, el archivo compilador/codigo.php es el que va a generar el archivo compilador/codigo-errores.log,
      mientras que hacer el proceso en la consola CMD obtendrá los resultados por medio de la carpeta compilador/dist, en la que se encuentra el archivo compilador.jar


7. ARCHIVO DE SALIDA
---------------------------------------------------------------------------------------------------
Nombre: <nombre>-errors.log, en la misma carpeta que el .php (codigo.php -> codigo-errors.log).
Si ya existe, se reemplaza.

Formato:
  - Cada línea del código fuente se copia precedida de su número con 4 dígitos y un espacio:
        0001 <?php
    El contenido después del prefijo es idéntico byte a byte al original, incluido su salto de
    línea original (\r\n, \n o \r). Con más de 9999 líneas el número crece a 5 dígitos
    (10000). El separador de un espacio está en la constante LogFormat.NUMBER_SEPARATOR.
  - Luego una línea vacía y la sección de errores, ordenada por línea, columna y código:
        Error <código>. Line <NNNN>. <descripción específica>
  - Si no hay errores se escribe: No lexical errors found.
  - El log se escribe con la misma codificación con la que se leyó el archivo (UTF-8 o
    ISO-8859-1).
  - Los mensajes de error están en inglés, tal como los define la especificación del proyecto.

8. CATÁLOGO COMPLETO DE ERRORES
---------------------------------------------------------------------------------------------------
Cada error indica el lexema o carácter exacto y, cuando es útil, la columna. Si en una línea
hay varios problemas, se reporta cada uno por separado. Los textos citados de más de 40
caracteres se recortan a 40 y se agrega "...".

8.1 Etiqueta de apertura <?php
  100  Texto antes de la etiqueta de apertura (en líneas anteriores o en la misma línea).
       Ejemplo:  echo "";   (línea 1)   <?php  (línea 3)
  101  Línea en blanco o espacios antes de <?php.        Ejemplo: "  <?php"
  102  Etiqueta mal escrita (no es exactamente <?php).   Ejemplo: <?PHP, <? php, <?=
  103  El archivo no contiene <? (se reporta en la línea 1). Ejemplo: archivo vacío.
  104  <?php pegado a otro carácter.                     Ejemplo: <?phpecho 1;
  105  Una segunda etiqueta de apertura.                 Ejemplo: ?> <p> <?php ...
  106  El archivo tiene BOM de UTF-8 (marca invisible al inicio). Guardar como UTF-8 sin BOM.

8.2 Etiqueta de cierre ?>
  110  No existe ?> (se reporta en la última línea). Si hay un ?> dentro de un comentario, el
       mensaje lo indica, porque ese ?> se ignora.
  111  Cierre mal escrito en la última línea.            Ejemplo: ? >
  112  Contenido en una línea posterior a ?> (un error por línea). Ejemplo: ?> y luego echo 1;
  113  Espacios o tabulaciones después de ?> en su misma línea.  Ejemplo: "?>  "
  114  Saltos de línea después de ?> (se cuentan todos, incluidas las líneas en blanco).
       Ejemplo: el archivo termina en "?>" + Enter.
  115  Texto después de ?> en la misma línea.            Ejemplo: ?> echo 2;
  116  Un ?> que no es el último del archivo (indica la columna).

8.3 Identificadores (solo el destino de la asignación =)
  200  Empieza con dígito después de $.                  Ejemplo: $1variable = 4;
  201  Carácter no permitido después de $, o $ solo.     Ejemplo: $-data = 5;  $ñame = 1;
  202  Carácter no permitido después del primero (uno por carácter, con su posición).
       Ejemplo: $na@me = 6;  (posición 4)
  203  El destino no empieza con $.                      Ejemplo: total = 7;
  204  El nombre es una palabra reservada (comparación exacta de mayúsculas).
       Ejemplo: $if = 10;   (pero $If = 3; es válido)
  205  No hay identificador a la izquierda de =.         Ejemplo: = 5;
  Palabras reservadas: class function if while echo else continue for return public null
  false true trim foreach private include print const do.
  Después de const se valida un nombre de constante (no necesita $). Ejemplo: const MAX = 10;

8.4 Comentarios
  300  Texto que parece continuar el comentario de la línea anterior.
       Ejemplo: $a = 1; // comentario    (línea 5)   continua aqui   (línea 6)
  301  Texto suelto que no es código PHP ni está marcado como comentario.
       Ejemplo: palabras sueltas
  302  Marcador de comentario mal formado: una sola / al inicio de una instrucción.
       Ejemplo: $c = 3; / comentario malo     (la división $a / $b NO es error)
  303  Comentario /* ... */ que ocupa varias líneas.
  304  Comentario /* que nunca se cierra.

8.5 Otros lexemas
  400  Cadena sin comilla de cierre. Ejemplo: $s = "sin cerrar;
  401  Carácter no reconocido, con su código Unicode. Ejemplo: € (U+20AC)
  402  Número seguido directamente de letras. Ejemplo: 12abc


9. DECISIONES DE DISEÑO
---------------------------------------------------------------------------------------------------
  - Mayúsculas en identificadores: los identificadores distinguen mayúsculas y minúsculas.
    $total y $Total son entradas distintas en la tabla de símbolos, y $if es error pero $If no.
    En cambio, una palabra suelta se clasifica como KEYWORD sin importar mayúsculas (ECHO es
    palabra clave), igual que en PHP. Ambas reglas son constantes en la clase ReservedWords.
  - "Include": el enunciado escribe Include con mayúscula; se trata como la palabra reservada
    include.
  - ?> dentro de un comentario: el contenido de un comentario de línea se ignora por completo,
    incluido ?>. En PHP real, ?> sí terminaría el comentario; aquí se sigue la regla del
    enunciado ("el contenido del comentario se ignora") y el error 110 lo explica.
  - Separador: entre el número de línea y el texto hay un espacio (0001 <?php). Si se requiere
    sin espacio, basta cambiar LogFormat.NUMBER_SEPARATOR a "".
  - BOM: la marca BOM de UTF-8 se detecta, se reporta como error 106 y no se copia al log,
    porque es un marcador de codificación y no un carácter visible.
  - Codificación: se intenta leer como UTF-8 estricto; si falla, se lee como ISO-8859-1. El
    log se escribe con la misma codificación.
  - Recuperación de cadenas sin cerrar: una cadena que llega al final del archivo sin su
    comilla termina al final de su propia línea (error 400) y el análisis continúa en la línea
    siguiente, para que no "trague" el ?> final.
  - Archivo sin <?: se analiza completo en modo PHP para que las demás validaciones se sigan
    ejecutando (además del error 103).
  - Sin librerías externas ni expresiones regulares: solo se usa el JDK. Cada patrón es un
    autómata escrito a mano y su Javadoc indica la expresión regular equivalente.
  - Identificadores solo ASCII: letras a-z y A-Z, dígitos y _. La ñ y las tildes no son
    válidas en identificadores.


10. SOLUCIÓN DE PROBLEMAS
---------------------------------------------------------------------------------------------------
  "java no se reconoce como un comando interno o externo"
     Java no está instalado o no está en el PATH. Instale un JDK/JRE 8 o superior y agregue su
     carpeta bin a la variable de entorno PATH (Panel de control > Sistema > Configuración
     avanzada > Variables de entorno). Cierre y vuelva a abrir CMD.

  Las tildes o la ñ se ven mal en la consola
     Ejecute "chcp 65001" en CMD antes de correr el programa. El archivo .log no se ve afectado:
     ábralo con un editor como Notepad o VS Code.

  Aparece el error 114 aunque el archivo "termina" en ?>
     La mayoría de los editores (incluido NetBeans) agregan un salto de línea al final del
     archivo al guardar. Un archivo correcto debe terminar exactamente en ?>, sin Enter
     después. Desactive la opción de "salto de línea final" del editor o borre ese último
     salto de línea.

  Después de compilar ya no está el .php en dist
     "Clean and Build" y "ant clean" borran la carpeta dist; el paso "-post-jar" de build.xml
     vuelve a copiar codigo.php e INFORME.txt. Si faltan, verifique que ambos archivos existan
     en la carpeta raíz del proyecto. Cualquier otro .php debe copiarse a mano.

  "ERROR: no file with the .php extension was found"
     El .php no está en la misma carpeta que el .jar, o su extensión no es exactamente ".php"
     (por ejemplo "codigo.PHP" o "codigo.php.txt"; en Windows active "Extensiones de nombre de
     archivo" en el Explorador para verla).

  "ERROR: could not write the log"
     La carpeta es de solo lectura o no tiene permisos de escritura. Copie el .jar y el .php a
     una carpeta donde pueda escribir.


11. LIMITACIONES
---------------------------------------------------------------------------------------------------
  - No se reconocen heredoc ni nowdoc (<<<).
  - No se analiza la interpolación dentro de cadenas con comillas dobles: la cadena completa es
    un solo token (por eso "$variable" dentro de una cadena no cuenta en la tabla de símbolos).
  - No se realiza análisis sintáctico ni semántico (por ejemplo, variables no declaradas).
  - Varios bloques PHP intercalados con HTML solo se reportan mediante los errores 105 y 116.
  - No se aceptan identificadores Unicode (solo ASCII).


12. USO DE INTELIGENCIA ARTIFICIAL GENERATIVA
---------------------------------------------------------------------------------------------------
12.1 Declaración
  Este proyecto se desarrolló con apoyo de herramientas de Inteligencia Artificial Generativa,
  como lo permite el enunciado (sección "Indicaciones Importantes"). El uso de IA se declara en
  esta sección y en un comentario de la clase principal (src/compilador/Compilador.java).

12.2 Herramientas utilizadas
  - Claude Code (Anthropic): asistente de programación que se ejecuta en la consola, con el
    modelo Claude Opus. Se usó desde la carpeta raíz del proyecto, en Windows.

12.3 Metodología de trabajo con la IA
  El proyecto no se generó con una sola instrucción. Se siguió un proceso en tres pasos:

  a) Especificación previa. Antes de generar código se redactaron dos documentos que la IA
     debía seguir y que se incluyen en la carpeta raíz del proyecto:
       - PRD.md: los requisitos del enunciado convertidos en reglas verificables (lectura del
         archivo, formato del log, catálogo de errores 100-402 con el texto de cada mensaje,
         arquitectura por etapas del análisis léxico y casos de prueba).
       - CLAUDE.md: reglas obligatorias para la IA (solo el JDK, sin librerías externas, sin
         expresiones regulares, código compatible con Java 8, no alterar el código fuente
         leído, formato exacto de los errores y una responsabilidad por clase).
         - Claude redactó ambos documentos.

  b) Construcción incremental. El programa se construyó con 10 prompts secuenciales
     (archivo PROMPTS.md, reproducidos en la sección 13). Cada prompt construye una parte del
     programa y termina con un paso de verificación ("Verify"). No se pasaba al siguiente
     prompt hasta comprobar que la verificación del anterior se cumplía.

  c) Ajustes posteriores. Con la IA también se tradujeron los comentarios del código a
     comentarios de una línea en español, se revisó el enunciado para identificar los
     requisitos de documentación del uso de IA y se redactó esta sección.

12.4 Partes del proyecto generadas con IA
  - El código fuente de todos los paquetes: app, io, lexer, lexer.pattern, validation,
    symbols, errors y report.
  - El ejecutor de pruebas test/compilador/FixtureRunner.java, los archivos de prueba de
    test-fixtures y sus bitácoras esperadas (test-fixtures/expected).
  - El borrador de este INFORME.txt.

12.5 Revisión y verificación realizadas
  El resultado de cada prompt se revisó y se probó antes de incorporarlo:
  - Se ejecutó el verificador FixtureRunner sobre los 16 archivos de test-fixtures. Comprueba
    que cada log es idéntico byte a byte al esperado, que la copia numerada reproduce el
    archivo fuente y que la concatenación de todos los lexemas es igual al texto original.
    Resultado: 16 aprobados, 0 fallidos.
  - Se ejecutó el .jar desde CMD con el codigo.php entregado por el profesor y se obtuvo
    "No lexical errors found." (sección 7.1).
  - Se comprobó que el código no usa java.util.regex ni librerías externas (solo java.*).
